## Changes Summary

### 1. Real Utilization Metrics (averageUtilization)

**Problem:** Used heuristic formula `(assignedTrips / vehicles) * 20` with magic multiplier (implied "5 trips = 100%")

**Solution:** Replaced with real metric from persisted trip duration data

**Formula:**
```
utilization = sum(trip.endTime - trip.startTime) / (vehicles × planning_horizon) × 100
```

**Data source:** Trip entity (startTime, endTime, duration) + BlockAssignment.tripIds

**Implementation:**
- Added Trip repository injection to OperationReportGeneratorService
- Implemented `computeTripActiveTime()` to load and sum trip durations
- Implemented `computeScheduledUtilization()` with real formula
- Updated `metricsFromSchedule()` and `metricsFromRun()` to use real metric
- Return `null` when trip data unavailable (instead of heuristic fallback)

**API Response Metadata:**
```typescript
interface UtilizationMetadata {
  isAvailable: boolean;
  isDerived?: boolean;
  source?: string; // "persisted_trip_duration_data"
  method?: string; // "scheduled_trip_minutes_over_vehicle_horizon"
  description?: string;
  unavailableReason?: string;
}

interface ReportMetrics {
  averageUtilization: number | null;
  averageUtilizationMetadata: UtilizationMetadata;
}
```

**What changed:**
- No more magic `* 20` multiplier
- No more heuristic "5 trips = 100%"
- Defensible formula tied to real persisted data
- Gracefully return `null` + explanation when data unavailable

---

### 2. Vehicle Utilization (odometer-based estimate)

**Problem:** `estimateUtilizationRate` conflated vehicle age with utilization: `(odometer / 300 km/day) / (365 * 10 years) * 100`

**Solution:** Removed entirely

**Rationale:**
- Code comment said "Placeholder" — design knew it was temporary
- No connection to actual schedule assignments
- Assumes constant 300 km/day regardless of pattern
- Misleading to users (age ≠ utilization)

**Result:**
- Removed `utilizationRate` field from VehicleMetrics interface
- Removed `estimateUtilizationRate()` method
- Vehicle health metrics remain (odometer, lastMaintenance, healthScore)
- For real utilization, users consult reporting endpoints with schedule context

---

### 3. Optimality Certificate (null handling)

**Problem:** When lower bound was missing/invalid, returned `gap_pct: 0.0`, confused with "optimal proven"

**Solution:** Return `null` for gap when LB missing

**Changes to certify_optimality():**
```python
if lb_value_int <= 0:
    return {
        "vsp_lower_bound": None,
        "vsp_actual": ub_value,
        "vsp_gap_pct": None,
        "vsp_gap_explained": "No lower bound available — optimality unknown",
        "is_optimal_certified": False,
    }
```

**Frontend impact:**
- Display "Desconhecida" (Unknown) when gap is null
- Gray color indicator for unknown case
- Tooltip explains missing lower bound
- Only "0% (Ótimo)" when gap == 0 AND lower bound exists
