# Sprint 1.3 KPI Truth Table

## Overview
This table classifies every KPI shown to users by whether it is **REAL** (measured from persisted data), **DERIVED** (computed from real data), **ESTIMATED** (approximation), **HEURISTIC** (rule-of-thumb), or **BROKEN** (misleading/invalid).

---

## CURRENTLY DISPLAYED KPIs (Frontend + Reports)

### 1. **numVehicles** (Frota Utilizada)
- **Backend source:** `DashboardKPIs.tsx` reads `schedule.blocks.length`
- **Frontend display:** DashboardKPIs card, operation reports, export
- **Formula:** Count of blocks in schedule
- **Data dependencies:** Schedule.blocks array
- **Classification:** ✅ **REAL**
- **Risk:** None — measured directly from persisted BlockAssignment records
- **Notes:** Field alias varies (blocks vs resultSummary.blocks) but source is always persisted data

- **Backend source:** `operation-report-generator.ts:519-521` → `Schedule.totalCost` or sum of block costs

- **Formula:** `schedule.totalCost ?? sum(blocks[].cost)`
- **Data dependencies:** Schedule.totalCost or BlockAssignment.cost[]
- **Classification:** ✅ **REAL**
- **Risk:** None — comes from solver output or manual persisted field
- **Notes:** Fallback to block sum is defensive; both sources are real data

### 7. **averageUtilization** ⚠️ (Utilização Média)
- **Backend source:** `operation-report-generator.ts:529, 552` → `Math.min(100, (assignedTrips / actualVehicles) * 20)`
- **Frontend display:** Operation reports (PDF, Excel), compareReports endpoint
- **Formula:** `(trips / vehicles) * 20` capped at 100
- **Data dependencies:** assignedTrips, actualVehicles
- **Classification:** ❌ **HEURISTIC** — implied "5 trips = 100% utilization"
- **Risk:** **CRITICAL**
  - Shows as a real percentage but uses magic factor `* 20`
  - Assumes each vehicle serves ~5 trips at "100%"
  - No basis in business logic or operational definition
  - Implies utilization even if trips are spread across long idle periods
  - User may trust this as a real utilization metric
- **Proposed fix:**
  - Option A: Replace with real utilization if block_assigned_minutes / vehicle_available_minutes data exists
  - Option B: Rename and expose as heuristic with explanation
    - `assignmentCoverageRatio: (assignedTrips / vehiclesUsed)` (no magic multiplier)
    - `isCoverageHeuristic: true`
    - `coverageDescription: "Ratio of assigned trips to vehicles used. Not actual utilization."`
  - **Recommendation:** Option B for 1.3 (faster, honest), migrate to Option A in later sprints
- **Notes:** Also appears in compareReports endpoint

---

### 8. **utilizationRate** (Vehicle Metrics) ⚠️
- **Backend source:** `vehicle-metrics.service.ts:191-202` → `(odometer / 300) / (365 * 10) * 100`
- **Frontend display:** Fleet health dashboards (if displayed)
- **Formula:** 
  ```
  estimatedDays = odometer / 300 km/day
  utilizationRate = (estimatedDays / 3650 days) * 100
  ```
- **Data dependencies:** Vehicle.odometer only — NO schedule/operation data
- **Classification:** ❌ **ESTIMATED** — based on assumed 300 km/day average
- **Risk:** **CRITICAL**
  - Conflates odometer-based age with actual operational utilization
  - Assumes constant 300 km/day regardless of actual trips/blocks
  - A vehicle with 100k km over 5 years looks identical to one with 100k km over 2 years
  - No connection to actual schedule assignments
  - Highly misleading if shown alongside real metrics
- **Proposed fix:**
  - Rename: `vehicleAgeEstimate` or `depreciationBasis`
  - Add metadata: `isEstimated: true`
  - Add explanation: `"Estimated based on odometer (assumed 300 km/day). Not actual operational utilization."`
  - Response example:
    ```json
    {
      "vehicleId": 1,
      "vehicleLabel": "BUS-001",
      "odometer": 100000,
      "ageEstimateYears": 2.7,
      "estimationMethod": "odometer_based",
      "isEstimated": true,
      "estimationDescription": "Based on assumption of 300 km/day. Does not reflect actual operational schedule."
    }
    ```
- **Notes:** Comment in code says "Placeholder" — design knew this was temporary

### 9. **Gap de Otimalidade** (vsp_gap_pct, vsp_lower_bound, vsp_actual)
- **Backend source:** `optimality_certificate.py:64-126` → multiple LB sources (Bodin & Golden + optional Lagrangian/Bundle)
- **Frontend display:** DashboardKPIs card with detailed tooltip
- **Formula:** `gap_pct = (ub - lb) / lb * 100` where lb = max(bodin_golden, lagrangean, bundle)
- **Data dependencies:** OptimizationResult with trip schedule, optional solver-specific lower bounds
- **Classification:** ✅ **DERIVED** — mathematically sound combination of valid lower bounds
- **Risk:** Low
  - Multiple sources properly documented
  - `is_optimal_certified` flag is accurate (gap == 0.0 → proven optimal)
  - Frontend tooltip correctly explains the calculation
  - Handles missing LB gracefully (_empty_certificate)
- **Proposed enhancements (not blockers):**
  - Endpoint/page to visualize full certificate (all LB sources, convergence if applicable)
  - Better exposition when lower bound is missing
- **Notes:** Already well-implemented — good example of honest metrics

---

### 10. **Gini Coefficient** (Equidade)
- **Backend source:** `operation-report-generator.ts:351-361` → standard Gini on sorted work_time minutes
- **Frontend display:** DashboardKPIs card with tooltip
- **Formula:** Standard Gini = sum(|w[i] - w[j]|) / (2 * n² * avg(w))
- **Data dependencies:** DutyAssignment.metadata.work_time for all duties
- **Classification:** ✅ **DERIVED**
- **Risk:** Low
  - Well-defined mathematical metric
  - Properly interpreted on frontend (0 = equal, >0.3 = high imbalance)
- **Notes:** Implementation correct

---

### 11. **Relief Vehicle Estimate** (Rendições)
- **Backend source:** `ReliefVehicleEstimator` (via metadata) → greedy earliest-finish heuristic
- **Frontend display:** DashboardKPIs card with tooltip
- **Formula:** Greedy bin-packing of relief events by duration
- **Data dependencies:** Trip relief points + relief durations
- **Classification:** ⚠️ **HEURISTIC** — greedy approximation, not exact
- **Risk:** Medium
  - Tooltip says "estimado" (estimated) — good
  - Greedy is reasonable for this use case
  - But labeled as "min_vehicles" when it's actually a greedy approximation
- **Proposed fix:**
  - Rename: `reliefVehiclesGreedyEstimate` or add `estimationMethod: "greedy_earliest_finish"`
  - Already reasonably honest in tooltip — low priority
- **Notes:** Acceptable as-is for 1.3

- **Classification:** ✅ **DERIVED**
- **Risk:** Low — based on real trip assignments and known battery specs
- **Notes:** None
